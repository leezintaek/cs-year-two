# Week 1 — Q&A

## Q1. 프로세서는 한 가지 일만 한다고 하는데, 그럼 여러 코어가 각각 1가지 일을 진행해서 코어가 많을수록 작업이 빠른 건가?

"프로세서는 한 가지 일만 한다"는 것은 코어 하나가 한 순간에는 명령어를 하나씩만 fetch-decode-execute 하는 순차적 제어 흐름(control flow)을 가진다는 뜻이다.

멀티코어는 이런 코어를 여러 개 붙여, 서로 다른 제어 흐름(명령어 스트림)을 동시에 실행하는 구조 — 이것이 병렬 처리(parallelism)다. 따라서 코어가 많을수록 이론적으로 처리량은 늘어난다.

다만 항상 비례해서 빨라지는 것은 아니며, 아래 조건에 따라 제한된다.

1. 소프트웨어가 멀티스레드/멀티프로세스로 작업을 나누도록 작성되어 있어야 여러 코어를 활용한다. 단일 스레드 프로그램은 코어 수와 무관하게 코어 1개만 사용.
2. 작업 자체가 나눌 수 있는(parallelizable) 성격이어야 한다. 순차적 의존성이 강하면 나누기 어렵다.
3. 코어들이 L3 캐시·메인 메모리를 공유하므로, 메모리 대역폭이 병목이 되면 코어가 늘어도 성능 향상이 기대만큼 나오지 않을 수 있다.
4. 코어 간 동기화·통신 오버헤드도 존재한다.

## Q2. DRAM이 refresh가 필요하다는 것의 뜻이랑 이유가 뭐야?

DRAM은 1비트를 커패시터(capacitor)에 저장된 전하로 표현한다(전하가 있으면 1, 없으면 0). 커패시터는 시간이 지나면 누설 전류(leakage current)로 인해 저장된 전하가 서서히 빠져나가며, 그대로 두면 전하량이 줄어들어 값을 구분할 수 없게 되고 데이터가 소실된다.

이를 막기 위해 DRAM은 데이터가 사라지기 전에 주기적으로 각 셀의 값을 읽어 다시 써주는(rewrite) 동작, 즉 refresh(재충전)를 계속 수행해야 한다. 이렇게 동적으로 계속 충전을 유지해야 해서 이름도 Dynamic RAM이다.

반면 SRAM은 커패시터가 아니라 플립플롭 형태의 회로(비트당 트랜지스터 6개)로 값을 유지하므로 전원만 공급되면 값이 안정적으로 유지되어 refresh가 필요 없다. 대신 회로가 복잡해 밀도가 낮고 비싸다.

## Q3. shell 부분에서 kernel과 bash는 어차피 메모리에 존재하는데, disk에도 만들어둔 이유가 뭐야?

방향이 반대다. **원본은 disk에 있고, 메모리에 있는 것은 실행하려고 disk에서 불러온(load) 복사본**이다. 슬라이드에서 disk에 `kernel`, `bash`, `ls`, `a.out`(hello)이 파일로 저장되어 있고, 메모리에도 kernel과 bash가 있는 것은 **지금 실행 중이기 때문**이다. `./hello`를 실행하면 hello도 같은 방식으로 disk에서 메모리로 복사된다.

disk에 반드시 있어야 하는 이유는 다음과 같다.

1. **메모리(DRAM)는 휘발성(volatile)이다.**
   - 전원이 꺼지면 메모리 내용은 모두 사라진다(Q2의 refresh 참고). 반면 disk(SSD/HDD)는 비휘발성이라 전원이 꺼져도 남는다.
   - 컴퓨터를 켤 때마다 kernel과 bash를 어디선가 다시 가져와야 하는데, 그 원본이 disk다.
   - 부팅 과정: 전원 ON → 부트로더가 disk에서 kernel 이미지(예: `/boot/vmlinuz`)를 메모리로 올림 → kernel 실행 → 로그인하면 kernel이 disk의 `/bin/bash`를 메모리로 올려 shell 실행.
2. **프로그램은 실행될 때만 메모리에 올라간다.**
   - 메모리는 disk보다 훨씬 작고 비싸다. 모든 프로그램을 항상 메모리에 둘 수 없으므로, 필요한 것만 그때그때 disk에서 load하고 끝나면 메모리에서 내린다.
   - bash도 마찬가지다. 터미널을 닫으면 그 bash 프로세스가 차지하던 메모리는 해제되고, 새 터미널을 열면 disk의 `/bin/bash`에서 다시 load한다. 터미널을 여러 개 열면 같은 파일로 bash 프로세스가 여러 개 생긴다.
3. **실행 중에도 메모리에 전부 있는 것은 아니다.**
   - 실제 OS는 프로그램 전체를 한 번에 올리지 않고, 필요한 부분(page)만 그때그때 load한다(demand paging, 이후 virtual memory에서 배움). 메모리가 부족하면 일부를 내렸다가 필요할 때 다시 disk에서 읽어온다. 따라서 실행 중에도 disk의 원본이 계속 필요하다.

정리하면 **disk = 영구 보관용 원본(파일)**, **memory = 지금 실행하기 위해 올려둔 작업용 복사본**이다. CPU는 disk에 있는 명령어를 직접 실행할 수 없고 메모리에 있는 명령어만 가져와 실행할 수 있으므로, "disk에 저장 → 실행 시 메모리로 load → CPU가 실행" 구조가 된다.

## Q4. 그럼 built-in이라는 게 메모리에 존재한다는 게 아니라, 전원 실행 시 자동으로 메모리로 옮겨진다는 의미인가?

둘 다 아니다. **built-in(내장 명령)은 "shell 프로그램(bash) 자체의 코드 안에 구현되어 있는 명령"** 이라는 뜻이다. 전원이나 부팅과는 관계가 없다.

| 구분 | built-in command | external command |
|---|---|---|
| 예시 | `cd`, `echo`, `export`, `exit`, `pwd` | `ls`, `gcc`, `cat`, `./hello` |
| 구현 위치 | bash 실행 파일(`/bin/bash`) **내부의 함수** | disk에 있는 **별도의 실행 파일** (`/bin/ls` 등) |
| 실행 방식 | bash가 자기 코드 안의 함수를 바로 호출 | bash가 새 프로세스를 만들고(fork), disk의 파일을 메모리로 load해서 실행(exec) |

- built-in이 메모리에 있는 것처럼 보이는 이유: bash가 실행될 때 bash 파일 전체(built-in 코드 포함)가 메모리로 load되기 때문이다. 즉 **bash의 일부라서 bash와 함께 올라와 있는 것**이지, built-in만 따로 미리 올려두는 것이 아니다.
- external command는 입력할 때마다 disk에서 해당 파일을 찾아 메모리로 load해야 한다. 강의 슬라이드의 "첫 단어가 built-in이 아니면 외부 명령으로 간주해 디스크에서 적재한다"가 바로 이 말이다.
- `cd`가 반드시 built-in이어야 하는 이유: 현재 디렉터리는 **각 프로세스가 가진 상태**다. `cd`를 별도 프로그램으로 만들면 새 프로세스의 디렉터리만 바뀌고 끝나므로 shell 자신의 디렉터리는 그대로다. 그래서 shell 내부에서 직접 처리해야 한다.
- 확인 방법: 터미널에서 `type cd` → `cd is a shell builtin`, `type ls` → `ls is /bin/ls`

## Q5. CPU 명령어 사이클의 decode는 기계어를 다시 어셈블리로 만드는 과정인데, 이렇게 하는 이유가 효율성 때문인가?

전제가 틀렸다. **decode는 기계어를 어셈블리로 바꾸는 과정이 아니다.** CPU는 어셈블리를 전혀 모르고, 처음부터 끝까지 기계어(비트)만 다룬다.

### decode가 실제로 하는 일
기계어 명령어는 여러 개의 **비트 필드**로 이루어진 이진수다. decode는 이 비트들을 해석해 **"이 명령어를 실행하려면 하드웨어의 어느 부분을 어떻게 움직여야 하는가"** 를 결정하고, 그에 맞는 **제어 신호(control signal)** 를 만드는 과정이다.

예: `48 01 d8` (= `add %rbx,%rax`)
- opcode 부분 → "덧셈이다" → ALU에 덧셈 동작 신호
- operand 부분 → "레지스터 rbx와 rax" → 레지스터 파일에서 해당 레지스터를 읽도록 선택 신호
- 크기 정보(`48` = REX.W 접두사) → "64비트 연산"
- 결과를 rax에 쓰도록 쓰기 신호

즉 decode는 **기계어 → 하드웨어 제어 신호**로의 변환이다. (x86 같은 복잡한 CISC 명령어는 decode 단계에서 내부의 더 단순한 micro-op(μop)들로 쪼개기도 하지만, 이것도 어셈블리가 아닌 CPU 내부 표현이다.)

### 어셈블리는 누구를 위한 것인가
어셈블리는 **사람이 기계어를 읽고 쓰기 위한 텍스트 표기법**일 뿐이다. 기계어와 거의 1:1 대응한다.

| 방향 | 과정 | 수행 주체 |
|---|---|---|
| 어셈블리 → 기계어 | assemble | assembler (`as`), 컴파일 과정의 일부 |
| 기계어 → 어셈블리 | disassemble | `objdump -d`, `gdb`의 `disas` 등 **사람이 보기 위한 도구** |
| 기계어 → 제어 신호 | decode | **CPU 하드웨어** |

week5·6에서 본 `(gdb) disas` 결과가 바로 "기계어를 사람이 읽을 수 있게 어셈블리로 보여준 것"이다. 이것은 디버깅·분석을 위한 것이며, CPU의 실행 과정과는 무관하다.

### 정리
- CPU 실행: 메모리의 기계어를 **fetch** → 비트 필드를 해석해 제어 신호 생성(**decode**) → **execute**
- 어셈블리로의 변환(disassemble)은 CPU가 하는 일이 아니라, **사람이 기계어를 이해하려고 도구로 하는 일**이다.

## Q6. 트랜지스터(transistor)와 캐패시터(capacitor)가 뭐야?

둘 다 컴퓨터 칩을 이루는 가장 기본적인 전자 부품이다. 한 줄로 요약하면 **트랜지스터 = 전기 스위치**, **캐패시터 = 전기를 잠깐 담아두는 작은 통**이다.

### 트랜지스터 (Transistor): 전기로 켜고 끄는 스위치
- 단자가 3개다. 그중 하나(gate)에 전압을 주면 나머지 두 단자 사이로 전류가 흐르고(ON = 1), 전압을 빼면 끊긴다(OFF = 0).
- 사람 손이 아니라 **전기 신호로 다른 전기 신호를 켜고 끈다**는 점이 핵심이다. 그래서 트랜지스터 여러 개를 연결하면 AND, OR, NOT 같은 **논리 게이트**를 만들 수 있다.
- 이 논리 게이트를 조합해 ALU, 레지스터, 캐시(SRAM), 제어 회로(decode 등) 등 **CPU 전체**를 만든다.
- 트랜지스터 수가 곧 칩의 규모다. 예: 8086(1978)은 약 2.9만 개, 최신 CPU는 수백억 개 (week5 Intel CPU 역사 참고).

### 캐패시터 (Capacitor): 전하를 저장하는 통
- 두 개의 도체 판 사이에 절연체를 끼운 구조로, **전하(전기)를 모아 저장**할 수 있다.
- 전하가 차 있으면 1, 비어 있으면 0으로 비트를 표현할 수 있다.
- 하지만 통에 작은 구멍이 난 것처럼 **시간이 지나면 전하가 새어 나간다(leakage)**. 그래서 주기적으로 다시 채워줘야 한다 → DRAM의 **refresh** (Q2 참고).

### 메모리에서의 쓰임

| 구분 | DRAM (메인 메모리) | SRAM (캐시) |
|---|---|---|
| 1비트 구성 | 트랜지스터 1개 + 캐패시터 1개 | 트랜지스터 6개 (캐패시터 없음) |
| 값 저장 방식 | 캐패시터의 전하 | 트랜지스터끼리 서로 붙잡는 회로(flip-flop) |
| refresh | 필요 (전하가 샘) | 불필요 (전원만 있으면 유지) |
| 특징 | 구조가 단순해 **밀도 높고 쌈**, 느림 | 구조가 복잡해 **비싸고 크지만** 빠름 |

- DRAM에서 트랜지스터는 캐패시터에 접근할지 말지를 정하는 **문(스위치)** 역할을 하고, 실제 값은 캐패시터에 담긴다.
- 이 차이 때문에 메모리 계층에서 **캐시는 SRAM(작고 빠름), 메인 메모리는 DRAM(크고 느림)** 으로 구성된다.

## Q7. [TF_quiz Q5] "외부 참조를 해결하는 과정을 relocation이라고 한다"가 틀린 이유는?

**정답: F**

외부 참조를 해결하는 과정은 **symbol resolution**이다. 링커는 두 가지 일을 한다.

| 단계              | 하는 일                                 |
|-------------------|-----------------------------------------|
| Symbol resolution | 각 symbol 참조를 정의와 연결            |
| Relocation        | 최종 주소를 정하고 하나의 파일로 합침   |

**Symbol resolution**
- `test.o`의 symbol table을 보면 `printf`는 `*UND*`(정의되지 않음)로 표시된다.
- 링커가 이 참조를 C 라이브러리(`libc`)에 있는 `printf`의 정의와 연결한다. → `printf@GLIBC_2.2.5`

**Relocation**
- `.o` 파일 안의 주소는 모두 0부터 시작하는 임시 주소이다 (`main`이 `0x0`).
- 링커가 여러 object를 합치면서 각 symbol에 실제 주소를 정해주고(`main` → `0x1149`), 그 주소를 쓰는 명령어들을 고쳐서 하나의 실행 파일(ELF)로 만든다.

**정리**: "외부 참조 해결 = symbol resolution", "주소 조정 + 결합 = relocation"

## Q8. [TF_quiz Q11] `objdump -t test.o`에서 `printf`가 `*UND*`로 표시되는 이유는?

**정답: T**

- `*UND*`는 **undefined**, 즉 "이 object file 안에서 사용은 하지만 정의는 없는 symbol"이라는 뜻이다.
- `test.c`는 `printf`를 호출만 하고, 함수 본체는 C 라이브러리(libc)에 있다. 그래서 assembler가 만든 symbol table에서 `printf`는 섹션이 정해지지 않은 `*UND*`로 남는다.

```
$ objdump -t test.o
0000000000000000 g  F .text  000000000000001e main     ← 정의됨 (.text 섹션)
0000000000000000    *UND*    0000000000000000 printf   ← 정의 안 됨
```

**같은 이유로 생기는 현상**
- `objdump -d test.o`의 `call` 명령어가 `e8 00 00 00 00`처럼 **주소 자리가 0으로 비어 있다.** 아직 `printf`의 위치를 모르기 때문이다.
- 이 빈칸은 링크 단계에서 채워진다.
  - symbol resolution: `printf` → libc의 `printf@GLIBC_2.2.5`와 연결
  - relocation: 실제 주소를 정하고 `call`의 빈칸을 수정
- 그래서 `.o` 파일은 완전한 프로그램이 아니라 **직접 실행할 수 없다.**

## Q9. [TF_quiz Q20] `F = (X+Y) - (X*Y)`를 레지스터 없이 계산하면 메모리 접근이 9번, 레지스터를 쓰면 3번인 이유는?

**정답: T**

**레지스터 없이 (매 명령어가 메모리에서 읽고 메모리에 씀)**

| 명령어 | 메모리 접근                       | 횟수 |
|--------|-----------------------------------|------|
| ADD    | X, Y 읽기 + 결과 쓰기             | 3    |
| MUL    | X, Y 다시 읽기 + 결과 쓰기        | 3    |
| SUB    | ADD·MUL 결과 읽기 + F 쓰기        | 3    |
| 합계   |                                   | 9    |

**레지스터 사용**
- X, Y를 한 번씩 읽어 레지스터에 둔다 → 2번
- ADD, MUL, SUB의 중간 결과는 모두 레지스터에 둔다 → 0번
- 최종 결과 F만 메모리에 쓴다 → 1번
- 합계 **3번**

**의미**
- 레지스터는 CPU 안에 있는 가장 빠른 저장 공간이다.
- 같은 값을 반복해서 쓰거나 중간 결과를 잠깐 보관할 때 메모리까지 다녀오지 않아도 되므로 메모리 접근이 크게 줄어든다.
- 메모리(DRAM) 접근은 CPU 사이클보다 훨씬 느리므로(강의 기준 15ns vs 0.5ns), 접근 횟수를 줄이는 것이 성능에 중요하다.

## Q10. [TF_quiz Q28] 전처리 결과물인 `.i` 파일이 binary file이 아닌 이유는?

**정답: F** (`.i`는 text file이다)

- 전처리기(cpp)는 `#`으로 시작하는 지시문만 처리한다.
  - `#include` → 헤더 파일 내용을 그대로 삽입
  - `#define` → 매크로를 값으로 치환
  - `#ifdef` 등 → 조건에 맞는 코드만 남김
- 결과는 **여전히 C 소스 코드**이므로 ASCII 문자로 된 text file이다. 강의처럼 `vi test.i`로 열어서 읽을 수 있다.

**컴파일 단계별 결과물**

| 단계          | 명령어         | 결과   | 형식   |
|---------------|----------------|--------|--------|
| Preprocessing | `gcc -E`       | `.i`   | text   |
| Compilation   | `gcc -S`       | `.s`   | text   |
| Assembly      | `gcc -c`       | `.o`   | binary |
| Linking       | `gcc -o hello` | hello  | binary |

- **text → binary로 바뀌는 지점은 assembly 단계**이다. assembler(as)가 어셈블리 코드를 기계어로 바꿔 object file(ELF)을 만든다.
- 그래서 `.o`는 `vi`로 읽을 수 없고 `objdump`, `nm`, `readelf` 같은 도구로 봐야 한다.

## Q11. [TF_quiz Q36] 2048×2048 배열 복사에서 `copyij`가 `copyji`보다 느리다는 말이 틀린 이유는?

**정답: F** (`copyij`가 훨씬 **빠르다**: 4.3ms vs 81.8ms)

```c
// copyij: 바깥 i, 안쪽 j          // copyji: 바깥 j, 안쪽 i
for (i = 0; i < 2048; i++)          for (j = 0; j < 2048; j++)
  for (j = 0; j < 2048; j++)          for (i = 0; i < 2048; i++)
    dst[i][j] = src[i][j];              dst[i][j] = src[i][j];
```

**1단계: C 배열의 메모리 배치 (row-major)**
- C의 2차원 배열은 **행(row) 단위로 연속 저장**된다.
- `src[0][0], src[0][1], ..., src[0][2047], src[1][0], ...` 순서로 메모리에 놓인다.

**2단계: 접근 패턴 비교**

| 함수     | 안쪽 루프 변화 | 다음 접근까지 거리           |
|----------|----------------|------------------------------|
| copyij   | j 증가         | 4바이트 (바로 옆)            |
| copyji   | i 증가         | 2048 × 4 = 8KB (한 행 건너뜀)|

**3단계: 캐시와의 관계**
- 캐시는 메모리를 한 바이트씩이 아니라 **블록(cache line, 보통 64바이트) 단위**로 가져온다.
- `copyij`: 한 번 가져온 블록 안의 int 16개를 연달아 사용 → 대부분 **cache hit**
- `copyji`: 매번 8KB 떨어진 곳을 읽음 → 가져온 블록에서 1개만 쓰고 다음 블록 필요 → 대부분 **cache miss**, 느린 DRAM 접근 반복

**정리**
- 두 함수는 **같은 계산, 같은 결과**인데 접근 순서만 달라서 성능이 약 **19배** 차이 난다.
- 강의 메시지: "Performance depends on **access patterns**" — 캐시를 잘 활용하는 코드가 빠르다.

## Q12. [TF_quiz Q46] "SRAM은 DRAM보다 빠르지만 비트당 트랜지스터 수는 더 적다"가 틀린 이유는?

**정답: F** (SRAM이 트랜지스터를 **더 많이** 쓴다)

| 구분          | SRAM                 | DRAM                       |
|---------------|----------------------|----------------------------|
| 비트당 구성   | 트랜지스터 6개       | 트랜지스터 1개 + 캐패시터  |
| 속도          | 빠름 (~2ns)          | 느림 (~15ns)               |
| 밀도          | 낮음                 | 높음                       |
| 가격          | 비쌈                 | 쌈                         |
| refresh       | 불필요               | 필요                       |
| 용도          | Cache                | Main Memory                |

- SRAM은 트랜지스터 6개로 flip-flop 회로를 만들어 값을 붙잡는다 → 빠르고 refresh가 필요 없지만, 부품이 많아 **밀도가 낮고 비싸다.**
- DRAM은 캐패시터에 전하로 저장 → 구조가 단순해 **밀도가 높고 싸지만**, 전하가 새서 refresh가 필요하고 느리다.

**함정 포인트**
- "빠르다 = 단순하다"로 연결하면 틀린다. SRAM은 **회로가 복잡한 대신(트랜지스터 많음) 빠르다.**
