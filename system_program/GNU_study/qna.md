# GNU Study — Q&A

## Q1. 디버깅 정보인 -g를 안 붙이면 디버깅 정보가 없어서 디버깅이 불가능해?

**A.** 불가능하지는 않다. 다만 **소스 코드 수준(source-level) 디버깅**이 안 되고, **기계어(assembly) 수준 디버깅**만 가능해진다.

### -g가 추가하는 것
`-g`는 실행 파일에 **디버깅 정보(DWARF 형식)** 를 넣는다. 여기에는 다음이 들어 있다.

- 기계어 주소 ↔ **소스 파일의 줄 번호** 대응 관계
- **지역 변수**의 이름, 타입, 저장 위치(스택/레지스터)
- 구조체·typedef 등 **타입 정보**

`-g`가 없으면 이 정보들이 없을 뿐, 프로그램 자체(기계어)는 그대로 있으므로 gdb로 실행하고 멈추고 메모리·레지스터를 들여다보는 것은 여전히 가능하다. gdb는 시작할 때 `(No debugging symbols found in a.out)` 라는 메시지만 띄운다.

### -g 유무에 따라 가능한 것

| 명령            | -g 있음 | -g 없음 |
|-----------------|---------|---------|
| list            | O       | X       |
| break main      | O       | O       |
| break file.c:10 | O       | X       |
| print var       | O       | X       |
| next / step     | O       | X       |
| backtrace       | O       | 일부    |
| stepi / nexti   | O       | O       |
| disassemble     | O       | O       |
| info registers  | O       | O       |
| x/4x $rsp       | O       | O       |

- `break main` : 함수 이름은 디버깅 정보가 아니라 **심볼 테이블(symbol table)** 에 들어 있어서 `-g` 없이도 동작한다.
- `next / step` : 줄 번호 정보가 없어서 "which has no line number information" 메시지와 함께 함수 끝까지 실행돼 버린다. 대신 `stepi`/`nexti`로 **명령어 단위**로 진행해야 한다.
- `backtrace` : 함수 이름은 나오지만 인자 값, 파일명, 줄 번호는 나오지 않는다.
- `print var` : 변수 이름을 모르므로 불가능. 대신 `x`로 메모리 주소를 직접 보거나 `info registers`로 레지스터 값을 봐야 한다.

### strip까지 하면?
`strip a.out` 이나 `gcc -s`로 **심볼 테이블까지 제거**하면 함수 이름도 사라진다. 이때는 `break main`조차 안 되고 `break *0x401136` 처럼 **주소로** 중단점을 걸어야 한다. 그래도 실행·정지·메모리/레지스터 조사는 여전히 가능하다 (리버스 엔지니어링이 바로 이런 상황에서 하는 디버깅이다).

### 참고
- `-g`는 디버깅 정보를 **추가만** 할 뿐 생성되는 기계어 자체는 (거의) 바꾸지 않는다. 그래서 실행 파일 크기만 커지고 실행 속도는 같다.
- 반대로 `-O2` 같은 최적화 옵션은 기계어를 바꾸므로, `-g -O2`로 컴파일하면 변수가 `<optimized out>`으로 나오거나 줄 순서가 뒤섞여 보일 수 있다. 디버깅할 때는 보통 `-g -O0`을 쓴다.

## Q2. 그럼 배포용 파일엔 디버깅 정보를 안 붙여?

**A.** 보통 **배포 파일 안에는 넣지 않는다.** 하지만 디버깅 정보를 아예 안 만드는 것은 아니다. 실무에서는 **`-g`로 빌드한 뒤 디버깅 정보를 별도 파일로 떼어 내서 보관**하는 방식을 많이 쓴다.

### 배포 파일에서 빼는 이유
- **파일 크기** : 디버깅 정보는 실행 코드보다 몇 배 커질 수 있다.
- **정보 노출** : 변수·함수 이름, 소스 경로, 타입 정보가 들어 있어 리버스 엔지니어링이 쉬워진다.
- 💡 **실행 속도는 이유가 아니다.** 디버깅 정보(`.debug_*` 섹션)는 실행할 때 메모리에 올라가지 않으므로 속도에는 영향이 없다.

### 그래도 버리지 않는 이유
배포한 프로그램이 사용자 환경에서 crash 나면 **core dump**만 받아서 원인을 찾아야 한다. 이때 디버깅 정보가 없으면 주소만 보이고 어느 함수, 몇 번째 줄인지 알 수 없다. 그래서 디버깅 정보는 개발자 쪽에 따로 보관해 둔다.

### 디버깅 정보를 분리하는 방법 (Linux)
```bash
gcc -g -O2 -o app app.c                          # 디버깅 정보 포함 빌드
objcopy --only-keep-debug app app.debug          # 디버깅 정보만 따로 저장
strip --strip-debug app                          # 배포 파일에서 디버깅 정보 제거
objcopy --add-gnu-debuglink=app.debug app        # 두 파일을 연결
```
- 사용자에게는 `app`만 배포하고, `app.debug`는 개발자가 보관한다.
- 나중에 core dump를 분석할 때 gdb가 `app.debug`를 찾아 읽으면 줄 번호, 변수 이름이 다시 보인다.

### 실제 사례
- **Linux 배포판** : 프로그램 패키지와 별도로 `-dbg`, `-dbgsym`, `-debuginfo` 패키지를 제공한다. 필요한 사람만 설치하면 된다.
- **Windows** : 디버깅 정보를 처음부터 실행 파일과 별개인 `.pdb` 파일로 만든다.

### 정리
- 개발용 빌드 : `-g -O0` (디버깅이 편하게)
- 배포용 빌드 : `-O2` + `-g`로 만든 뒤 디버깅 정보는 분리 보관, 배포 파일은 strip

## Q3. -rwxr-xr-x 이건 뭐야?

**A.** `ls -l`로 파일을 볼 때 맨 앞에 나오는 **파일 타입 + 접근 권한(permission)** 이다. 총 10글자로, 1글자(타입) + 3글자 × 3그룹(권한)으로 나뉜다.

```
-  rwx  r-x  r-x
│   │    │    └─ others : 나머지 모든 사용자
│   │    └────── group  : 파일 소유 그룹에 속한 사용자
│   └─────────── user   : 파일 소유자
└─────────────── 파일 타입
```

| 구간     | 문자 | 대상          | 의미           |
|----------|------|---------------|----------------|
| 1번째    | -    | 타입          | 일반 파일      |
| 2~4번째  | rwx  | user (소유자) | 읽기·쓰기·실행 |
| 5~7번째  | r-x  | group         | 읽기·실행      |
| 8~10번째 | r-x  | others        | 읽기·실행      |

### 1번째 글자 — 파일 타입
- `-` : 일반 파일 (regular file)
- `d` : 디렉터리 (directory)
- `l` : 심볼릭 링크 (symbolic link)

### r, w, x의 의미
`-`는 해당 권한이 **없다**는 뜻이다.

| 문자 | 파일      | 디렉터리       |
|------|-----------|----------------|
| r    | 내용 읽기 | 목록 보기 (ls) |
| w    | 내용 수정 | 파일 생성·삭제 |
| x    | 실행      | 들어가기 (cd)  |

디렉터리에서 `x`가 없으면 안의 파일 이름을 알아도 접근할 수 없다.

### 숫자(8진수) 표기
각 권한을 숫자로 바꿔 3글자씩 더하면 한 자리 숫자가 된다.

| 문자 | 값 |
|------|----|
| r    | 4  |
| w    | 2  |
| x    | 1  |
| -    | 0  |

- `rwx` = 4+2+1 = **7**
- `r-x` = 4+0+1 = **5**
- 따라서 `-rwxr-xr-x` = **755**

### 자주 보는 조합
- `755` (`rwxr-xr-x`) : 실행 파일, 디렉터리. 소유자만 수정, 모두 실행 가능
- `644` (`rw-r--r--`) : 일반 파일 (`.c` 소스 등). 소유자만 수정, 모두 읽기 가능
- `600` (`rw-------`) : 비밀 파일 (SSH key 등). 소유자만 접근

### 바꾸는 방법 — chmod
```bash
chmod 755 app       # 숫자로 지정
chmod +x script.sh  # 모두에게 실행 권한 추가
chmod u+x,g-w file  # 소유자 실행 추가, 그룹 쓰기 제거
```

### gcc와의 관계
`gcc -o app app.c`로 만든 실행 파일은 자동으로 `x` 권한이 붙어 `-rwxr-xr-x`로 나온다. 그래서 `./app`으로 바로 실행할 수 있다. 반면 직접 만든 셸 스크립트는 `644`로 생성되므로 `chmod +x`를 해 줘야 `./script.sh`로 실행된다.
